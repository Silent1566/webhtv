## 1. 要实现的用户能力

用一句话说：**同一个 WiFi 下的其他人，不应该能随便往你的电视/手机上推视频、装 APK、改设置或拉走你的配置。**

局域网接收入口没有统一的身份校验：播放推送、偏好修改与配置同步不能仅凭请求里的设备信息区分已配对设备和其他设备。

**可借鉴但需改造的两点**（照搬会踩坑）

1. PC 的 `isPeerAuthorized(peerAddress)` 用的是**调用方 IP**；NAT/多网卡/热点共享下 IP 不稳定，uuid 才是主键。移植时以 uuid（本仓 `Device.getUuid()`）为主、IP 只作辅助提示。

## 4. 方案对比（历史提案，最终决策见 §11–12）

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A. 不改 | 维持现状 | 零成本 | 同网段任何人可推流/装包/改设置/拉配置 | 否 |
| B. 只加总开关 | 一个"允许局域网控制"开关，默认关 | 半小时能做完 | 开了就全开，无法区分"我的手机"和"邻居的电脑"；自家 7 条链路每次都要手动开 | 不足 |
| C. 总开关 + 共享令牌（配对码） | 电视显示 6–8 位配对码，手机首次配对后本地保存 32B 令牌（复用 `ProxyCapabilityToken`），之后请求带 `X-WebHTV-Token` | 一次配对长期有效；不依赖 IP；实现面小（1 个校验点 + 1 个存储 + 5 处调用点带头）；可撤销（重新生成即失效） | 需要一条配对 UX；令牌是"全权"，不能按端点/按对端细分 | **推荐：S1** |

| E. C + 端点分级 | 在 C 之上把写端点分层：`setting/file/sync/apk*` 需要令牌**且**本机开关；`push/cast/control` 仅需令牌；`/device`、`/tvbus`、只读查询保持开放 | 风险面收敛最干净；符合 PC 协议文档"settings 单独确认"的思路 | 端点分类表要写死并测 | **推荐：并入 S1** |

## 5. 初始推荐方案（已由 §11–12 替代）

**S1（本轮建议实施）**

1. 新增 `LanAccessControl`（纯逻辑 + 一层轻存储）：总开关（默认 **关**）、令牌生成/校验（复用 `ProxyCapabilityToken`）、端点分级表。
2. `Action.doResponse` 在 `doJob` 之前做一次校验：未授权 → `403` + 明确 message（`LAN access disabled` / `unauthorized peer`），**且不再把未知 do 当成功**（改 400）。
3. 配对 UX：设置 → 增强功能 → "局域网授权"，页面显示配对码与"重新生成"（重新生成即让所有旧令牌失效）；手机端首次推送失败时提示"请在电视上查看配对码"。
4. 自家 7 条调用点补齐请求头 + 一条"未配对则引导配对"的错误分支。
5. `/device`、`/tvbus`、只读查询类保持开放（发现层与 EPG 依赖它们，且不含隐私/写操作）。

**S2（后续，需重新授权）**：把单一令牌升级为"已授权设备列表"（uuid 白名单），支持按设备撤销；令牌退化为配对过程中的一次性凭据。

## 6. 验收标准

- 未配对客户端 `curl /action?do=push` → `403`，响应与日志都不含令牌明文。
- 关闭总开关时**任何** `do=` 都 403（含只读的 `search`），仅 `/device`、`/tvbus` 可用。
- 未知 `do=` → `400`（不再 200）。
- 配对后：手机推送 URL、一键同步、推 APK 三条链路在模拟器双端实测通过。
- 令牌只在内存与加密偏好中出现；`Action.java:68` 那行日志必须脱敏（当前会把 params 全量打进日志）。
- 单测覆盖：开关关闭、令牌错误、令牌正确、端点分级、未知 do —— 纯逻辑层（不依赖 Android）先红后绿。

删除 `LanAccessControl` 与 `Action` 的校验分支、移除 7 处请求头即可回到今天的行为；不涉及数据迁移，旧令牌留在偏好里无害。

## 9. 风险

- **兼容性**：老版本 App（没有配对逻辑）将无法再推送到新版设备。这是安全修复的必然代价，必须在更新说明里写清；总开关默认关也会让"升级后一切照旧"的预期落空，需要产品确认。
- **配对可发现性**：配对码藏在设置里，用户第一次推送失败容易懵；错误文案必须直指位置。
- **令牌泄漏面**：持有凭据即代表设备身份；不得经明文 HTTP 传送受保护请求，也不得进入日志、历史或推送记录。后续接线必须验证受保护通道确实成立（见 §12）。
- **误伤自家功能**：`Manage.java:639` 的远端同步与 `ApkUrlPush` 走的路径不同，改动要逐条实测，不能只看编译通过。

## 10. 初始决策问题（历史记录）

1. **总开关默认值**：默认关（安全，但升级后自家推送立刻失效，需引导配对）还是默认开（升级无感，但"开=任何人可推"只解决一半）？我推荐**默认关 + 首次推送失败时引导配对**。
2. **令牌还是白名单先行**：S1 只做令牌（1 天量级），还是直接做 S2 的 uuid 白名单（2–3 天）？
3. **端点分级边界**：`bookmark/search/refresh` 这类"非写但也不公开"的端点，要求令牌还是继续开放？
4. **是否限制网段**：要不要像 PC 那样只接受与设备同网段的请求？我倾向**不做**——热点共享/多网卡下误伤概率高，令牌已经解决了"谁在用"的问题。

## 11. 已定决策（2026-11-27，用户确认）

| # | 决策 | 结论 |
|---|---|---|
| 1 | 总开关默认值 | **默认关**；自家客户端首次推送被 403 挡住时，界面引导"去电视上看配对码" |
| 2 | 第一阶段范围 | **直接做 uuid 白名单**（对齐 PC 的 `isPeerAuthorized` 语义），不做"先令牌、后白名单"的两步走 |
| 3 | 令牌的定位 | 降级为**配对阶段的一次性凭据**（TV 生成配对码 → 手机带着自己的 uuid 提交 → TV 允许后写入白名单并立即作废该码） |
| 4 | 端点分级 | 按第 4 节 E 方案：`setting/file/sync/apk*` 需白名单**且**本机开关；`push/cast/control/refresh` 需白名单；`/device`、`/tvbus`、只读查询保持开放 |

因此第 5 节的 S1 调整为"白名单版"，S2 取消（其内容已并入 S1）。实施顺序随之改为：

1. `LanPeerAuthorization`（纯 JVM）：白名单增删查、配对码一次性校验、端点分级判定；单测先红后绿。
2. 持久化：参照 `GitCloudTokenStore`，接收端加密保存设备 UUID、凭据摘要及用于列表展示的信息；不存 IP。
3. 先验证身份与受保护通道，再在请求体解析、日志及副作用前校验（拒绝 403、未知动作 400）。
4. 设置页「局域网授权」：总开关（默认关）、已配对设备列表（可撤销）、本机发放配对码。
5. 第一方客户端经受保护通道提供设备标识和凭据；未授权时引导配对。
6. 模拟器双端实测（5554 发送、5556 接收）：未授权 403、配对后三条链路可用、撤销后立即失效。

## 12. 第 1 步范围与安全修正（2026-11-27）

本节覆盖 §4–11 中 UUID 与传输的旧口径。白名单按 UUID 管理、总开关默认关、不按网段限流的产品选择不变。`Device.identityUuid()` 来自 `Device.java:70–80,95–98` 的 Android ID，用作标识而非秘密；单独提交 UUID 不构成授权。`Util.getAndroidId()`（`Util.java:390–396`）异常时使用固定占位值；内核拒绝将该值登记为设备。保留现状不能限制接收；只移植 PC 的对端标识检查不能证明设备身份；采用按设备配对并校验独立凭据的窄适配，不引入新依赖。

- 参考：[OWASP Authorization Cheat Sheet（Deny by Default、Validate the Permissions on Every Request）](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)；[NIST SP 800-63B-4（一次性认证秘密、限次与受保护通道）](https://pages.nist.gov/800-63-4/sp800-63b.html)。官方指南，2026-11-27 查阅。这里借用原则，不声明符合 NIST 身份认证等级。PC 同族源码及测试见 §3；本仓随机凭据与定时安全的比较先例是 `ProxyCapabilityToken.java:21–44`。
- **纯 JVM 验收**：总开关默认关闭；已知接收操作都要验证配对得到的 UUID 与设备凭据；`file/setting/sync/apk/apk_url` 再要求本机的敏感操作开关。`Action.java:127–131,172–176` 的 `search` 会触发搜索、`danmaku` 会写入播放会话，不能当只读放行。无效动作映射 400；已知但拒绝的动作映射 403。`/device`、`/tvbus` 不属于本内核。
- **配对验收**：进程内、同一时刻只有一个有效的随机 8 位码；有效期 2 分钟，失败 5 次失效，成功只消费一次。成功生成独立的 32 字节随机设备凭据，接收端内核只保留摘要；换码、撤销、重新配对不会继续接受对应的旧码或旧凭据。关闭接收清除未消费配对码，不清空已配对设备。
- **后续接线闸门**：不能仅传 UUID、不能把配对码或设备凭据送进明文 HTTP；先验证端到端的对端身份与受保护通道，再在解析请求体和产生日志/副作用前执行校验。持久层后续保存各设备的验证摘要，发送端保存对应凭据。此阶段没有客户端、监听端口、存储迁移或运行行为变化。
- **回滚**：撤回第 1 步提交即可；服务没有接线，无设备数据需要迁移。

## 13. 受保护通道证据（2026-11-27）

- 互为身份的是**两份本地自签证书的 SHA-256 指纹**，不是 UUID、也不是平台信任库。客户端只接受固定指纹的服务端证书，服务端要求对端出示证书并校验指纹；两侧都用 `SSLContext` 注入固定指纹的 `X509TrustManager`，未使用 `OkHttp.hostnameVerifier(true)` 之类的全局放行。
- 出口只绑定 `127.0.0.1` 的临时端口，用一次握手交换一行应用数据后即关闭；**没有**接入 `Nano`/端口 9978，也没有改变现有 HTTP 行为。
- 复核依据：[RFC 9525 §6](https://www.rfc-editor.org/rfc/rfc9525.txt)（用 `subjectAltName` 核对对端身份）；[OkHttp 5.4.0 CertificatePinner KDoc](https://raw.githubusercontent.com/square/okhttp/parent-5.4.0/okhttp/src/commonJvmAndroid/kotlin/okhttp3/CertificatePinner.kt)（自签证书必须先被 `TrustManager` 接受才能固定）；本机 `nanohttpd-2.3.1` 的 `makeSecure`/`SecureServerSocketFactory` 签名（说明最小可用做法是独立 TLS 监听，而不是在原监听上叠加）。
- **Android 运行时已复验（2026-11-27，两台模拟器 API 28）**：把同一份 `LanSecureChannel` 打成临时 dex，用 `app_process` 分别在 emulator-5554（服务端，证书 a）与 emulator-5556（客户端，证书 b）上运行，经 `adb forward/reverse` 桥接后握手成功——客户端拿到 `ack-from-5554`，即服务端已验证对端指纹并与应用数据交换。
  - 负例 1（冒名对端）：客户端改用证书 attacker 连接同一服务端，服务端日志中 `SERVER_RECEIVED` 计数为 **0**——未通过对端校验的请求根本没有进入应用处理。
  - 负例 2（客户端指纹不符）：客户端把期望指纹换成 b 而服务端仍是 a，握手在客户端即被拒，服务端同样 0 次进入处理。
  - 过程中发现并修正的**测试夹具**问题（非产品缺陷）：JDK 21 默认生成的 PKCS12 用 PBES2，Android BC 报 `1.2.840.113549.1.5.12 SecretKeyFactory not available`；改用 `PBEWithSHA1AndDESede`/`PBEWithSHA1AndRC2_40` 后两端均可加载。`java.nio.file.Path.of` 在 API 28 上同样不可用（仅影响临时 runner）。
  - 观察到的残留现象：服务端完成一次交换后 `app_process` 在退出阶段会打印 `RuntimeInit` 的 kill 栈；正例的结论来自客户端收到的 `ack-from-5554`（该 ack 由处理器内部写出），负例结论来自服务端处理器零进入。
- **配对结果已有可落盘格式（2026-11-27）**：`LanPeerRegistry` 定义明文格式 `{"version":1,"devices":[{"id","key"}]}`，只存 UUID 与 32 字节摘要的十六进制；解码不抛异常、不信任载荷——版本不符、条目畸形、摘要长度不对一律丢弃，条目数超过 64 直接返回空表而不是截断。内核新增 `partners()`（防御性拷贝）与 `restore(...)`（校验后整体替换；空表或超限表不改动现状）。6 例 JVM 测试覆盖往返保真、坏数据、上限与恢复后旧凭据仍可用。
